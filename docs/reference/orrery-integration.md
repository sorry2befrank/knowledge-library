# Orrery integration reference

This is a sanitized source map and adopted adaptation contract. Current code and future controls are distinguished below. Logical IDs identify source files without workstation locations. All example persona IDs and paths are fictional. No registry entry, canonical machine schema, status snapshot, scheduler or source file is installed by this reference pack.

## Current persona and write behavior

`orrery/lib/armillary/personas.ts`, `PersonaDef` and `loadPersonaRegistry`, currently preserve only `key`, `name`, `pillar`, `home`, `manifest` and `enabled`. Entries need string keys and homes; additional fields are discarded. `getPersona` excludes disabled entries, but that filtering is not a universal write guard. A home's arbitrary string value does not establish an approved root, volume identity or no-reparse guarantee.

The adopted controls `runtimeOwner`, `execution`, `rehearsal` and `homeWrites` are **new adaptations**. For the external librarian the adopted values are `knowledge-library`, `external`, `external`, and `false`. Existing personas need compatibility defaults preserving behavior. Invalid or ambiguous external combinations must be held. The routing key and full learner manifest ID need an explicit mapping; neither dotted-key inference nor a display title grants authority. No entry is added until Integration enablement (DESIGN.md §8.8, Landing, rollback and when registered folders open), in an attended window after A28 and A36 pass against the merged code. The dormant O1 package keeps the registry byte-identical.

## Reporting, learning and shared identity

`orrery/lib/armillary/personas.ts`, `parseFourFields`/`fileReport`, carries MOVED/BLOCKED/HIRING/NEXT; first non-empty captured field wins and subsequent incidental field text does not replace it. The Library projection must use bounded fixed templates and confirmed outcomes; HIRING defaults to none. Do not append external BLOCKED prose to commons in the first integration: `tasksFromCommons` can turn it into practice. A future commons path needs dedupe and external-owner exclusion first.

Turnovers/CORRECTIONS remain Library-owned attributed records. Orrery receives authorized metadata and bounded summaries, not executable skills or archive instructions. The external passdown section is written to Orrery data. The learner's scoped F/L trust stays authoritative in the Library; generic ladder outcomes are display-only and cannot grant removal or promotion rights. Duplicate syncs never earn another streak. See the separate report, correction and ladder references for their complete source mappings.

`orrery/lib/types.ts`, `Project`, presently uses the absolute project path as identity, with disk-derived `archived` and owner-set `archivedManual`. The integration adds a local versioned overlay joining stable integrationProjectId, collectionId/folderId, authorized scope and owner-approved alias revision. Removing an individual note never sets either project archive flag or changes registry/pillar membership. Private workstation aliases stay local and are excluded from this pack. Missing content is deliberate only when exact identity, current mapping and completed focus receipt agree.

It is a field/meaning inventory, **not a new JSON schema or alternative encoding**. PR #1 with the reviewed S1c implementation merged at `50f3f811ce7e64cf32ac21e079e3b33444def029`. The canonical references below bind this pack to that merged schema and its shared synthetic fixtures. The local lane's Orrery consumer (DESIGN.md §8.7, Orrery-side work package) remains future work and must flag disagreements rather than silently adapting. In particular, the contract distinguishes envelope identity from `proof.backupSnapshotId` and `proof.backupSnapshotHash`, and requires the operation's nullable `runId`, `planId`, `goalHash`, `policyHash` and `reasonCode`. The round-4 clarifications below are recorded in the merged S1c rulings. Schema and producer verification do not implement Orrery's approval-hash comparison or its local acceptance and filesystem integration. Synthetic cases here remain semantic input facts, not wire-format payloads; binding their references does not claim wire-schema validation, signature execution or live integration.

A goal-bound focus proposal is inspectable and implies no transfer or removal; a written veil narrows agents' content search and moves nothing. State meanings are independent: pushed means received, exact-version custody means preserved, indexing means search/read coverage, READBACK_OK means dated exact-byte readback, SNAPSHOT_OK means the identified backup includes that item. HELD/HELD_OK describe progress; a completed RECEIPTED operation proves working-folder removal only with its move and hold receipts and the schema-required readback and backup proof. HELD_PURGED is a later renewed-guard operation. Requested restoration is pending; a verified restore receipt is version/target-specific. RECREATED, CONFLICT_HELD_CHANGED and GUARD_REFUSED (any result) are conflict/blocked evidence. Offline/stale is an availability overlay, not a failed historical preservation claim. Same-volume holding alone reclaims no content bytes. "Preserved" means verified custody only (`verifiedNotIndexed + indexed`); received-only versions are excluded. Merged S1c corrected the producer, which at the S1b review also counted received-only versions.

The Library service assembles and signs each snapshot. `kl` fetches it and writes the signed bytes byte-for-byte to the Library-owned outbox; a queued weekly snapshot waits for the next attended `kl` run. Orrery's adapter only reads that outbox: it never deletes, renames or writes there. It validates the enrolled producer, signature and exact-byte digest, schema, current scope/identity and proof relationships, then atomically installs the accepted projection and checkpoint in Orrery's own data after checkpoint handling. A consumer that re-reads a snapshot whose wrapper digest or `snapshotId` equals its accepted checkpoint stops before the monotonic-sequence check. A duplicate is a no-op, not a rollback. Other snapshots require a monotonic sequence; rollback/new-key/scope changes require reconciliation. The Library prunes its outbox by sequence only after reading Orrery's accepted checkpoint (DESIGN.md §8.3, One evidence envelope; S1b D4, Signed wrapper). Limits in the adopted contract are 1 MiB and 100 recent operation summaries, explicit truncation, no more than one publication per minute, five-second adapter budget and a short lock timeout. A signature identifies the producer; it does not establish semantic truth or resist unrestricted same-user compromise.

Freshness is sync-first: use `lastSuccessfulSync` whenever known; use the consumer's own acceptance time only when sync is null. The consumer supplies that acceptance time to the validator. The envelope's `observedAt` caps **either selected reference**, both a known sync and the acceptance fallback: the earlier timestamp wins. Fresh producer time cannot refresh an old sync or supply a missing consumer observation. With neither sync nor acceptance, freshness is unknown. If sync or observation is later than the consumer's clock by more than two minutes, freshness is unknown. Historically, S1b's reference validator at fa7a2bd used the later of sync and acceptance, and the original S1c ruling 5 explicitly capped only the acceptance fallback. Merged S1c incorporates the round-4 clarification that caps both selected references. A stale or unknown-connectivity snapshot keeps each milestone's verdict and adds the stale/unknown overlay. Historical proofs stay dated rather than becoming failures merely because the host is idle (S1b D3, Semantics; DESIGN.md §8.4, State mapping and the Atlas flow).

The pack's `fresh`/`stale`/`unknown` maps to S1b's `freshness`; for `unknown`, ignore S1b's `stale` boolean. This overlay takes precedence over `state.availability`, which the producer at the S1b review always sets to `online`. The prose milestone names map to the wire names as follows: custody → `ingest-custody`, retrieval → `retrieval-index`, recovery → `recovery`, focus-removal → `focus`. Runtime cases use those wire names. The pack's `evidence-absent` means no snapshot at all; S1b's `absent` fixture means an accepted snapshot with zero operations, making every enabled milestone `unproven`.

## Atlas verdict and activation

`orrery/lib/armillary/hub.ts`, `flowHealth`, reads the Atlas flow/step graph and judges source-backed steps. A first `breaks` step yields `blocked` and makes downstream steps `unreached`; otherwise any `unknown` step yields `unproven`; otherwise the verdict is `verified`. An unmapped step is unknown. `orrery/scripts/flow-health.mjs` publishes that projection and preserves per-step state/evidence; `nextCheck` is a lead, not proof.

The new flow must declare the enabled milestone. An optional, disabled focus operation cannot block a proved read-only deployment. Safe refusal is successful guard behavior while the requested removal is still blocked. Per S1b D3, a receipt for a different source version leaves a structurally valid snapshot accepted and makes only that milestone `unproven`. The v1 proof carries a source version but no run or policy field, so run and policy binding is a consumer check (declared v1 omission, decision 2026-10-04 23:50). After whole-snapshot schema validation, the adapter compares the selected latest attempts' `goalHash` and `policyHash` with the hashes Orrery approved. Superseded historical attempts cannot poison a later matching attempt. A null operation hash mismatches an approved non-null hash for **every milestone**, including `ingest-custody`; there is no silent ingest exemption. A mismatch makes an otherwise non-blocking latest attempt `unproven`. A failed result or blocking stage still wins as `blocked`; hash mismatch never downgrades it. Merged S1c records these hash-scope and precedence clarifications; the future Orrery adapter must implement the approval comparison.

Within each milestone, latest attempts are keyed by `sourceVersion`, which the schema requires on every operation. `runId` is not part of that key. Find the newest timestamp first. **Grade every attempt at that timestamp**, including its approved goal/policy hash comparison, exact source-version proof, stage and result, before selecting the worst outcome (`blocked` before `unproven` before `verified`). A tied attempt with null or mismatched hashes or a cross-version proof must not disappear because a stage-only winner was chosen first; reversing input order cannot change the verdict. Older attempts' semantic mismatches remain superseded. Thus one run covering many versions keeps every version separate, while a later-run retry replaces an older failure for the same version. Across a milestone's latest attempts, any blocked attempt makes the milestone `blocked`; otherwise all attempts must be verified for `verified`; otherwise it is `unproven`. Pending, skipped, missing attempts, non-proving stages and cross-version proof errors cannot verify a milestone. No attempts is `unproven`, never vacuously verified. A stale/unknown overlay does not rewrite these verdicts.

A completed attempt verifies a milestone only at a proving stage with that stage's receipt. Schema validation comes first: every completed operation requires its source version/hash proof and all stage-specific fields in the canonical schema; the table is a semantic stage gate, not a reduced proof schema.

| Wire milestone | Proving stage and receipt |
|---|---|
| `ingest-custody` | `CUSTODY_OK`, or `COMMITTED` with `proof.custodyReceipt`; the schema requires that receipt at both completed stages. |
| `retrieval-index` | `INDEXED` with exact-version proof. |
| `recovery` | `RESTORED` with `proof.restoreReceipt`. |
| `focus` | `RECEIPTED` with move and hold receipts (and the schema-required readback/backup proof), `HELD_PURGED` with purge receipt (and required hold receipt), or `VEIL_WRITTEN` with `proof.veilReceipt`. The merged S1c schema includes `veilReceipt`; a veil claims no removal. |

`GUARD_REFUSED`, `CONFLICT_HELD_CHANGED` and `RECREATED` block the operation's **own milestone**, whichever milestone it belongs to and whatever its result; `failed` blocks that milestone at any stage. They do not propagate a block to unrelated enabled milestones. Every other completed stage is unproven: progress, not proof. Examples are `RECEIVED`, `PLANNED`, `FRESH`, `READBACK_OK`, `SNAPSHOT_OK`, `HELD`, `HELD_OK`, `RESTORE_REQUESTED`, and `CUSTODY_OK` under focus. The runtime `evidence-failed-guard` case uses wire stage `GUARD_REFUSED`; that stage blocks whatever the result. Merged S1c records this milestone scope, resolving the earlier ambiguous phrase "block every milestone".

In partial-coverage cases, `requiredItemProof: unknown` means a pending or missing latest attempt for a listed version (S1b `partial` and `partial-within-milestone`). The counts in `state.indexing.*` and `state.custody.*` are display facts and never change a milestone verdict; inconsistent state counts are a separate snapshot-validation failure, not evidence of success. For truncation, the producer lists every blocked and unproven latest attempt before any verified one, and truncates only the tail. The ordering check covers latest attempts from **all operation milestones**, including disabled ones; it must not filter to enabled milestones before checking the visible snapshot's order. If a truncated snapshot breaks that order, every enabled milestone is `unproven`, including one with a visible blocked attempt. That whole-snapshot ordering rule takes precedence over ordinary per-milestone grading; the diagnostic failure remains visible and cannot become a success claim. Without truncation, an operation under a disabled milestone does not affect an enabled milestone's verdict. A compliant truncated snapshot still applies the ordinary latest-attempt verdicts. A consumer cannot infer hidden operations: the producer-side synthetic `omittedLatestAttempts` inventory is not a wire field. Its fixture therefore states `producerOrderAccepted` and `producerSemanticSuccessClaim` separately from the `consumerVerdict` obtained from the visible snapshot.

Absent or partial proof never becomes success merely because a process ran. Public presentation uses fictional fixtures; private accepted data is not sent to a public renderer for later redaction.

Library integration is default off. First sync is attended or explicitly operation-triggered and observational; it adds no clock job, nightly stage or model call. Owner-selected Orrery goals are proposals until transaction-bound owner approval binds goal/policy revisions. No global delivery-policy change is required for an observational external adapter. The canonical schema is now published by the S1c merge; Orrery adapter implementation, activation, registry entry, real snapshot, approved canary and any production data remain separate release gates.
